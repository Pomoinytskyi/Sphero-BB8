# Step 2 — iOS Application

Two targets: a platform-free Swift package (`BB8Kit`) and a SwiftUI app
(`BB8Droid`) that consumes it.

```
ios/
├── BB8Kit/                    Swift package — no CoreBluetooth, no SwiftUI
│   ├── SpheroProtocol.swift     the codec, ported from bb8ctl/protocol.py
│   ├── SpheroDecoder.swift      frame reassembly and sync/async demux
│   ├── Sensors.swift            masks, 400 Hz divisor, sample decoding
│   └── Control.swift            deadzone, expo, drive models, profiles
└── BB8Droid/                  the app
    ├── DroidLink.swift          CoreBluetooth transport + connection lifecycle
    ├── Transmitter.swift        single-slot drive cell, deadline paced
    ├── GamepadInput.swift       GameController + on-screen fallback
    ├── Lighting.swift           the light show
    ├── DroidController.swift    60 Hz control loop
    ├── PreviewHarness.swift     synthetic state, for a Simulator with no radio
    └── Views/ContentView.swift
```

## Why the split

`BB8Kit` imports nothing but Foundation. That is what lets `swift test` run the
entire codec and control suite from the command line, with no simulator, no
device and no droid — the same property that made the Python side developable
between hardware sessions.

It is also the seam the app is built around: `DroidLink` is only responsible for
moving bytes, and knows no protocol.

## Cross-implementation verification

`GoldenVectorTests` loads `bb8_vectors.json` — generated by `bb8ctl vectors` on
the Python side — and asserts the Swift codec produces **byte-identical** output
for every command, plus matching characteristic UUIDs, handshake order, sensor
masks and field ordering.

This is the payoff of building the CLI first. The Python implementation was
verified against real hardware; these tests transfer that verification to Swift
rather than requiring it to be re-earned. A divergence fails the build instead of
producing a droid that behaves subtly differently.

**44 Swift tests, none requiring hardware.**

## What the hardware measurements changed

| Finding | Consequence in the app |
|---|---|
| `SOP2=0xFE` honoured | Drive loop never waits on a reply |
| Write-without-response: 89 pkt/s vs 16.7 | `.withoutResponse` on the drive path, `.withResponse` for setup |
| Deadline pacing needed | `Transmitter` advances a deadline rather than sleeping an interval |
| `SET_STABILIZATION` mandatory | Sent in `configure()`; without it ROLL is silently inert |
| Sensor param is a 400 Hz divisor | `SpheroSensors.divisor(forHz:)`, never milliseconds |
| Battery at `[2..3]` not `[1..2]` | `Sphero.PowerState` parses the verified layout |

The throughput headroom is what makes the light show free: driving at 30 Hz plus
lighting at 10 Hz uses under half the measured ceiling. Lighting still goes
through the transmitter's background lane, which only uses ticks the drive loop
did not want — so it is *structurally* unable to add latency, not merely
unlikely to.

## Input

`GCExtendedGamepad` via the GameController framework. An Xbox One S pad pairs
natively in Settings since iOS 13 and reports named inputs, so bindings survive a
controller swap — unlike the positional `get_button(2)` in the original notebook.

`GCVirtualController` presents an on-screen stick through the *same* interface,
so the touch fallback costs no extra control code.

| Input | Action |
|---|---|
| Left stick | Drive |
| RB (hold) | Aim — rotates the heading reference without driving |
| A | Reset aim |
| B | Emergency stop (latches until the stick recentres) |
| X | Absolute ↔ tank |
| Y | Tortoise ↔ rabbit |

## Safety

- `SET_MOTION_TIMEOUT` armed at connect: firmware stops the droid ~2 s after
  commands cease.
- Backgrounding the app issues an immediate stop. iOS suspends the control loop,
  and the firmware timeout would catch it a couple of seconds later — but two
  seconds of unattended droid is two too many if it is pointed at a staircase.
- E-stop latches until the stick recentres, so releasing the panic button does
  not resume driving.

## Building

```bash
xcodebuild -scheme BB8Droid -sdk iphonesimulator \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

```bash
cd ios/BB8Kit && swift test
```

The Simulator has no Bluetooth radio, so the app cannot connect there. Launch
with `-preview` to drive the interface from synthetic telemetry:

```bash
xcrun simctl launch booted com.vitalii.BB8Droid -preview
```
